# Decisions

Decisions that shape the project. Changing one needs the maintainer's approval; record the
answer here with the date. Background and details: [PLAN.md](PLAN.md).

| # | Date | Decision | Why / notes |
|---|---|---|---|
| D1 | 2026-11-18 | **Two repositories.** `rmxp3ds` (this repo: plan, converter, patch sets, depth profiles, tools, CI) and `mkxp-z-3ds` (fork of mkxp-z, the runtime), included here as the git submodule `runtime/`. Runtime changes go through a PR on the fork first, then a separate PR here bumps the submodule pointer. | Keeps the fork rebaseable on upstream mkxp-z and its license separate. PLAN §8. |
| D2 | 2026-11-18 | **Licenses.** `rmxp3ds`: GPL-3.0. `mkxp-z-3ds`: GPL-2.0-or-later (inherited from mkxp-z). Every new source file carries an SPDX header. Third-party code is recorded in `THIRD_PARTY.md` before it is copied. Avoid GPL-3.0-only code in the runtime (e.g. RetroArch `ctr_svchax.c`) unless the maintainer agrees. | PLAN §9. |
| D3 | 2026-11-18 | **New Nintendo 3DS only.** Old 3DS is out of scope until after M4. | CPU, RAM and second core budget. PLAN §1, §2. |
| D4 | 2026-11-18 | **RGSS1 only** (RPG Maker XP, Pokémon Essentials). No RGSS2/RGSS3. | PLAN §1. |
| D5 | 2026-11-18 | **CRuby via mkxp-z**, cross-compiled for `arm-none-eabi` (newlib/libctru), same Ruby version as mkxp-z embeds. mruby only as a fallback if CRuby proves infeasible. | Compatibility with Essentials scripts; ISeq precompile needs the identical version. PLAN §3.1. |
| D6 | 2026-11-18 | **citro3d renderer** replaces OpenGL; native `Tilemap`, `Sprite`, `Plane`, `Window`, `Viewport`; tone/blend via TEV combiners. | PICA200 has no programmable fragment shaders, textures ≤ 1024 px, power-of-two. PLAN §3.1. |
| D7 | 2026-11-18 | **Dual-core snapshot rendering.** Core 0 runs Ruby and produces an immutable frame snapshot; core 1 uploads dirty textures and renders both eyes. Ruby never waits on the GPU. | gpSP 3D pattern. PLAN §3.1. |
| D8 | 2026-11-18 | **Converter in Ruby** (`convert/`), with native `Marshal` access to `.rxdata` and minimal RGSS class stubs. | PLAN §3.2. |
| D9 | 2026-11-18 | **Agent testing with headless Azahar + mcp-azahar** inside the dev container; the runtime's self-reporting test mode for repeatable tests on emulator and console. Emulator results prove correctness only; performance numbers count only from a real New 3DS. | PLAN §6. |
| D10 | 2026-11-18 | **Development environment.** The dev container (`.devcontainer/`) is the reference environment: CI builds and uses its image, and it works with local Docker (devcontainer CLI / VS Code). The maintainer's Coder workspace (Kubernetes pod, no Docker, no `/dev/dri`) does not run the container; the toolchain is installed directly in the workspace following the Dockerfile, with the same pinned versions (`tools/setup-workspace.sh`). The default `devcontainer.json` stays portable; GPU access and host networking are an opt-in variant in `.devcontainer/linux-host/`. The image is Debian trixie with devkitPro copied from the pinned `devkitpro/devkitarm` image (Azahar and makerom need glibc ≥ 2.38; devkitPro's package servers reject cloud IPs). | Maintainer's choice (2026-11-18) over an envbuilder template or Docker-in-workspace. Risk: drift between workspace and image; mitigated by one script and the pinned versions shared with the Dockerfile, and by CI as the gate. |
| D12 | 2026-11-18 | **The CRuby 3DS port lives in the fork** (mkxp-z-3ds, GPL-2.0-or-later): configure flags, patches to Ruby 3.1.3 and the newlib shim go next to mkxp-z's own Ruby patches (`subprojects/packagefiles/ruby-3.1`) plus a 3DS build entry point. rmxp3ds keeps the benchmark/test apps (`tools/bench`) that build against `runtime/`. Replaces the top-level `ruby/` of PLAN §8. | Maintainer's choice (2026-11-18): one source for M1 and the runtime from M3 on, as the mkxp-z Switch/Vita ports do. |
| D11 | 2026-11-18 | **M2 is a go/no-go gate.** The maintainer decides on continue / scope down / alternative based on console measurements. | PLAN §4. |
| D13 | 2026-11-18 | **M2 result: go, full scope.** CRuby 3.1.3 on the New 3DS stays the approach; Essentials games remain the target as planned; M3 (runtime integration) is next. Tracked risks with their own measurements: startup time (~29 s to a new game in the demo: script parsing and data loading from SD; plan: precompiled bytecode and data caching in the converter), battle animations (not covered by M2), and GC spikes. | Maintainer's decision on hardware run 2 (NOTES.md, 2026-11-18): game logic 2.5–5.2 ms per 33.3 ms frame; with Essentials' Ruby sprite updates 22–25 ms, about half of that in the Ruby tilemap that M4 replaces natively (extrapolated ~15 ms); battle 115 ms per turn; 39 MB of 88 MB heap. |
| D14 | 2026-11-18 | **Renderer architecture: mkxp-z's GPU interface on citro3d.** The upstream display classes (Sprite, Bitmap, Window, Tilemap, Graphics, …) and mkxp-z's GPU wrapper layer (TEX/FBO, buffers, Quad/QuadArray, ShaderSet, GLState) stay as they are. Everything draws through one GL function table (`gl`, `src/display/gl/gl-fun.h`); on the 3DS that table is an implementation of the GL ES 2 subset mkxp-z uses, on citro3d (fork `3ds/display/gl3ds.cpp`):<br>• **Textures, FBOs:** PICA textures and render targets, padded to a power of two. Textures over 1024 px are stored as several pieces inside the table.<br>• **Buffers, DrawElements:** vertex buffers and draws.<br>• **Shader programs:** each of mkxp-z's known programs becomes a fixed TEV-combiner preset. The few that need real fragment programs (hue change, blur) fall back to the CPU.<br>• **Blend, scissor, viewport, clear, read-back.**<br>The dual-core snapshot (D7) becomes a command queue inside the table (M4). Rewriting the display classes for the 3DS stays the fallback if performance problems show up. | Maintainer's choice (2026-11-18). The display classes reach the GPU only through this table: about 400 uses of the wrapper layer, about 19 direct `gl.` calls, and about 60 distinct GL functions in all. This keeps all RGSS behaviour upstream's, the diff small and upstream merges easy. It replaces the per-class rewrite proposed in the M3 desk analysis (NOTES.md). |
| D15 | 2026-11-18 | **Game resolution: fit the screen height, pillarbox.** The game screen is rendered directly at 3DS height: scale 240/H (RGSS1 640×480 at 0.5 to 320×240; Essentials 512×384 at 0.625 to 320×240), centered on the 400×240 top screen with black side bars. Bitmaps keep their full resolution and are sampled when drawn. Implemented with mkxp-z's Hires screen scaling (`framebufferScalingFactor`, default 0.5, per game via `mkxp.json` / converter profile). Per-game overrides (e.g. crop to fill) remain possible through profiles. | Maintainer's choice (2026-11-18) over "fill width, crop top/bottom" and "native size, scroll". The PICA200 renders only into VRAM (6 MB; citro3d `C3D_RenderTargetCreateFromTex`). At 640×480 (padded to 1024×512, 2 MB each) the 2–3 screen buffers do not fit; at 320×240 they take 0.5 MB each. Small text loses legibility. |
